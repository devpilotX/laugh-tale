- Two-person rule strength - 17.4 says "Two-person rule for permanent bans **where possible**: one issues, one reviews" VS 19.14 lists "/ban (player) (reason) | Permanent ban, with the two-person rule (17.4)" - matters because one wording is best-effort and the other reads as a hard gate; the difference decides whether /ban blocks until a second staff member confirms - a builder cannot decide whether a single Admin can complete a permanent ban alone.

- /top is claimed by two commands - 19.5 lists "/top | Teleport to the highest safe block above you" VS 19.7 lists "/leaderboard [category] | /lb, /top rp" - matters because "/top rp" as a leaderboard alias collides with /top as a teleport that 15.4 requires to carry a warmup and cooldown; a mistyped leaderboard query would trigger a teleport - a builder cannot decide which behaviour /top has.
- /voice mute exists at two tiers with two meanings - 19.10 gives all players "/voice mute (player) | Mute one player for yourself only" VS 19.13 gives Mod "/voice mute (player) (duration) | Server-side voice mute" - matters because the two differ only by an argument, so an argument-count mistake in a Mod's command silences a player for everyone instead of for one listener - a builder cannot decide whether the server-side mute needs its own command name.

## RISKS ON A 2 vCPU / 4 GB HOST

- /rtp (15.2) generates and loads new chunks on demand. Chunk generation is the single heaviest sustained operation on a small box; even with the required async pre-generation, the pool refill competes for the same two cores. A synchronous fallback would spike MSPT well past 25 ms.
- /tpall and /tphereall (19.14) move every online player at once, forcing simultaneous chunk loads and entity tracking updates for the whole playerbase in one tick window.
- The live map (18.5) is explicitly "disk and CPU heavy" and the spec already concedes "If it costs measurable MSPT after tuning, turn it off". On 2 cores a render pass and the game loop cannot both have a core.
- Serving map tiles or any HTTP from the game host contradicts 18.1 and adds a public listener on the box, which is both CPU load and a flood target that would lag the game.
- Uncached web leaderboards (18.4) let the public internet trigger database work per page view. The 60-second cache and scheduled precompute are load-bearing mitigations, not optimisations.
- Aggregate queries behind /baltop, /leaderboard, /stats, /kd, /playtime and /transactions (19.3, 19.7) scan large tables. Any of these on the main thread violates 19.17's "No command may block the main thread on a database call".
- /ah search and /market (19.4) run text search and order-book aggregation over potentially large listing tables, on player-triggered demand with no stated rate limit value.
- Block-log operations, /lookup, /audit (player) and /audit full (19.12, 19.14, 19.15) read the largest tables on the server; a wide lookup can hold a connection and heap for a long time in 4 GB.
- Particle cosmetics from 19.8 (wings at Warrior, trail at Raider) produce continuous per-player packet output; with many players visible this is bandwidth and main-thread work. The 16.2 particle-density control is the only stated mitigation and it is player-side.
- Voice chat (16.2, 18.6, 19.10) adds a persistent audio path with its own threads and bandwidth alongside the game loop on two cores.
- Hourly database and six-hourly world backups (19.16) contend for disk with the game's own chunk writes; a world backup during peak play is a stall risk.
- Genuinely undetectable /vanish (19.12) requires packet-level interception, which adds per-packet work on the netty path for all observers.
- Twenty homes per player plus persisted per-player preferences (15.1, 16.3) enlarge the per-player row set and the startup load; small individually, but it is one more thing that must be async and cached rather than read per command.
- The Discord two-way relay (18.6) holds an outbound websocket and an HTTP client in the same JVM, adding heap and threads to a 4 GB box.
- The 100 ms per-command response budget (19.17) applied across every command in section 19 is only achievable if all of the above are async and cached; the spec sets the target but names no measurement or enforcement mechanism.
