## RISKS ON A 2 vCPU / 4 GB HOST

- Combined allocations exceed physical RAM by design - 30.2 states "The combined 4.5 GB exceeds the box, and that is acceptable **only** because the two never run together", with overallocation enabled and enforcement "by procedure"; a single mis-sequenced start puts 4.5 GB of limits plus 950 to 1350 MB of host overhead onto a 4 GB box and invites the OOM killer
- Production allocation at the top of the overhead range leaves no headroom - 29.4's own table (350 to 450 MB OS and Docker, ~100 MB Wings, 500 to 800 MB Panel) plus a 3.0 GB allocation reaches 4.35 GB on a 4 GB box
- Dev heap headroom below the stated floor - 1.5 GB allocation with `-Xmx 1.0 GB` leaves 512 MB, and 1.0 GB with `-Xmx 768m` leaves 256 MB, against 29.4's "never less than 768 MB, outside the heap"; the stated failure mode is a freeze, "which is harder to diagnose"
- Panel co-located on the tick-critical box - 29.5 records the cost as "500 to 800 MB and some CPU on the box whose tick budget is already tight", and PHP-FPM plus the queue worker and scheduler cron contend for the same 2 vCPU that must hold MSPT
- The three-hour full-load memory test runs while Panel, Wings and Docker compete for both cores - 29.4 requires it "at full expected player load", so the MSPT measured during it is a worst-case number and must not be confused with the launch baseline
- Chunk pregeneration on the VPS - 29.9 offers "simply pregenerating on the VPS overnight" as the alternative to transferring region files; pregeneration saturates both cores and the disk, so it cannot overlap any performance measurement
- Any agent tooling on the game box - 30.3 forbids it precisely because "an agentic CLI running on a 2-vCPU box competes for CPU with the very server it is measuring"; running Kiro, a linter, or a test harness on the VPS invalidates measurements
- Per-session and per-deploy hashing of every tracked config file (29.6, 30.4 item 5) adds disk and CPU load on the game host; safest while the server is stopped
- Pre-deploy backups of world, database and plugin data (29.8 step 5) plus the restore verification are heavy I/O on a box with no stated separate data partition, which 29.3 only "recommends"
- Deleting the stock server late (29.13c) keeps its allocation and port reserved while dev and production allocations are already overcommitted, tightening the node memory limit further
