## CONTRADICTIONS

- Secret rotation versus the Panel APP_KEY - Appendix E requires a script to "Rotate and redeploy **every credential**" VS the global never-break rule "Never regenerate the Panel `APP_KEY`. Encrypted panel data becomes permanently unrecoverable, even with database backups." - a literal implementation of the rotation script destroys the Panel irrecoverably on first run - the builder cannot decide the exclusion list (APP_KEY only, or also the database encryption key, the backup encryption key, and the store webhook secret) without the owner.
- Category-only plugin list versus the pinned manifest rule - Appendix A is "deliberately by category, not by brand" and defers selection to build time with "tick cost **measured after installation**" VS the never-break rule "Never install a plugin that is not in the manifest with a pinned version and a checksum." - measurement requires installing first, the manifest requires approval first; the two orderings are mutually exclusive - the builder cannot decide whether a measurement-only trial install on `laughtail-dev` is exempt from the manifest rule.
- Rollback permission model - Appendix A says of block logging "Rollback must be **permission-separable** (14.2)", implying a grantable node held by some staff role VS Appendix G which lists "**Owner-only rollback** - Rollback is a duplication vector, and log purging destroys evidence" - one says separable and delegable, the other says owner-exclusive - the builder cannot decide whether any admin group may ever hold the rollback node.
- CR versus RP as the rating quantity - Appendix D defines `combat_ratings` as "UUID, current CR, peak CR, season" VS `champions` as "Season number, UUID, **final RP**, awarded at" in the same table on the same page - two different abbreviations for what appears to be one rating value, with no conversion stated - the builder cannot tell whether RP is a derived seasonal score or a rename of CR, and therefore cannot write the season reset correctly.
- Who owns the schema for plugin-backed data - Appendix D opens "Use schema migrations **from the first commit. Never modify a live schema by hand**" and then outlines `balances`, `transactions`, `homes`, `claims`, `punishments` as project tables VS Appendix A which requires those same domains to be delivered by third-party plugins ("Economy provider - a single-currency ledger with transaction logging and an API", "Punishments - Database-backed", "Core commands and homes - Must store data in the database, not flat files (15.1)", "Land claims - Trust levels, an accrual model ... an API") - third-party plugins create and migrate their own tables, so our migrations would collide with theirs - the builder cannot decide whether these are our tables, plugin tables, or read-only views over plugin tables.
- Hardcoded-value CI grep versus the voice config - Appendix E requires a "Hardcoded-value check - Greps for IPs and absolute host paths. **Runs in CI** (5.1)" VS Appendix C which requires a "voice config - **Port, bind address**, codec settings, permissions" - a bind address is normally a literal IP, so the mandated config content will trip the mandated CI gate - the builder cannot decide the allowlist policy without the owner confirming which literals may be committed.
- Concurrency budget versus the restore drill and load test - the global environment rule states "The two servers must never run at the same time. Combined allocation exceeds the box" VS Appendix E which requires a "Restore drill - Restores the latest backup into a **scratch environment** and verifies integrity. Monthly, logged (5.4)" and a "Load test - Bot ramp plus event scenario (6.8)", and Appendix C which requires a "Compose file - **The four services** (5.2)" - a scratch restore target and a bot swarm are additional concurrent workloads on a box that is already stated to be over-committed with two servers - the builder cannot decide whether the drill runs off-box (which needs a second host and therefore money) or on-box with the dev server stopped.
- Appendix C omits config files for components Appendix A makes mandatory - Appendix A mandates "Anti-cheat", "Auction house", "Block logging", "Backup", "Chat management", "Discord bridge", "Live map", "Store integration", "Chunk pregeneration" VS Appendix C's nineteen-file list which contains no file for any of them (only `economy.yml` "Taxes, fees, sinks, dynamic band, floor" plausibly covers auction fees) - the config inventory is presented as the authoritative list of files to create but does not cover the component list - the builder cannot tell whether those components are configured entirely through vendor defaults or whether files are missing from the list.

## RISKS ON A 2 vCPU / 4 GB HOST

- Twenty-six mandatory component categories in Appendix A is itself the largest risk: even at a low per-plugin cost, 26 components plus Paper plus the Pelican panel will not leave a safe heap margin under the rule that at least 25 per cent or 768 MB stays outside `-Xmx` on a 4 GB box.
- Live map, "Async rendering, marker control" - tile rendering is CPU and disk-write heavy and will contend for one of only two vCPUs; on a 2-core box async rendering competes directly with the tick thread rather than hiding behind spare cores.
- Block logging, "Database-backed, inspection, lookup, preview, rollback" - high-volume synchronous-ish writes plus unbounded table growth with no retention value stated in Appendix D; disk fill is a realistic outage cause on a small VPS.
- Anti-cheat, "Simulation-based, off-main-thread" - movement simulation is one of the most CPU-expensive plugin classes; "off-main-thread" only helps if a spare core exists, and with 2 vCPU there is effectively none during a war event.
- Voice chat as a separate service with its own "codec settings" - a second resident process consuming RAM and continuous UDP bandwidth on the same box as the game server, competing during exactly the moments voice is used most.
- Chunk pregeneration, even "Async, resumable" - saturates both cores and the disk; Appendix A's "Run before launch, not during" is the only mitigation and it must be enforced operationally.
- The Appendix E load test's bot ramp runs on the same 2-core box that is being measured, so bot CPU inflates MSPT and the derived player cap is measured against a corrupted baseline.
- The Appendix E restore drill's "scratch environment" is a third concurrent workload against an environment already documented as over-committed with two servers, so it either needs a maintenance window or another host.
- Holograms and cosmetics particles - Appendix A concedes naive implementations are costly ("Scoreboard and tab ... Measure it; naive implementations are surprisingly expensive") and both are per-viewer packet generators on the main thread; without the `watchdog.yml` degradation ladder actually wired they are an unbounded tick cost during events.
- Order book matching (`orders`, `order_matches`) - a custom matching engine doing multi-row transactional writes per fill will spike MSPT if it runs on the tick thread during a busy market period.
- Nightly economy audit plus weekly economy report plus the scheduled health check all query the same database the live server writes to; overlapping schedules on 2 vCPU can starve the server thread during the window.
- The Appendix C compose file's "four services" plus the Paper heap plus page cache for world files leaves little room for the database buffer pool, so heavy `transactions` and `combat_events` write volume will push the database to disk I/O.
- Backup, "Consistent database dump plus world archive, offsite upload, encryption" - compression and encryption are CPU-bound and will consume a full core for the duration; running it while players are online will be visible in MSPT.
- `stats` "All tracked statistics per player (9.8)" with an unspecified shape - if implemented as row-per-stat with frequent updates it becomes the highest-write table on the server.
