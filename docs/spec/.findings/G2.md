## CONTRADICTIONS

- online-mode blocks the required bot load test - 6.4 sets `online-mode` to "true" and calls it "Mandatory (Section 3.2)" VS 6.8 mandates "Write a bot harness (`scripts/loadtest.js`) using a headless client library. Bots join, spread out, move, break and place blocks" and ramps to 40 bots - headless bots cannot authenticate against Mojang, so an online-mode server rejects them and acceptance 6-1/6-2 becomes untestable - the owner must choose: buy/borrow premium accounts, temporarily flip online-mode off behind a firewall on dev, or add a cracked-auth bypass plugin (each has a different security consequence)
- Watchdog top band sits above the hard-fail line - 6.1 sets normal-play hard fail at "over 40 ms sustained" VS 6.6 treats "40-48 ms" as a middle band and only alerts the Owner and captures spark "over 48 ms sustained 30 s" - the server can sit in a documented hard-fail state for an unbounded time with no Owner alert - a builder cannot decide whether the alert threshold is 40 or 48 ms
- Event MSPT target versus watchdog cosmetic kill - 6.1 allows "MSPT, during a war event | under 40 ms" VS 6.6 turns "Cosmetic particles off entirely. Non-essential holograms off." at 40-48 ms, while 6.8 requires the event scenario be run with "cosmetics on" - during exactly the event the spec was written for, cosmetics will be killed by the watchdog, so the event acceptance test measures a different configuration than live play - owner must decide whether events get a raised watchdog band
- max-players is pre-committed and simultaneously deferred to measurement - 6.4 states `max-players` "24" as the value at 2 cores / 4 GB VS 6.8 states "Do not guess the player cap. Measure it." and "set `max-players` from the measured number, not from hope" while predicting only "comfortable to roughly 20-24 players" - if the load test yields 18, one instruction says ship 24 - a builder cannot decide which value is authoritative before launch
- PvP everywhere versus a no-PvP spawn - 7.2 states "PvP | On everywhere" and 7.3 states "There is no safe zone anywhere in the survival world" VS 7.5 requires spawn be a "Protected region. No PvP, no block interaction, no mob spawning." - spawn is in the Overworld, i.e. the survival world - a builder cannot decide whether spawn-camping at the spawn platform is legal, and the rules board wording depends on the answer
- Restore drill needs a second server running - 5.4 requires "restore the latest backup into a throwaway container and join it" monthly VS the project's standing environment rule "The two servers must never run at the same time. Combined allocation exceeds the box" - a joinable restored Paper instance is a second server on the same 4 GB box - owner must decide whether drills run on a separate temporary VPS (a cost) or with the dev server stopped
- Host auto-updates versus the mid-build freeze - 5.5 requires "Automatic security updates for the host OS" VS never-break rule 13 "Never upgrade host OS packages or Docker mid-build without a fresh VPS snapshot first" - unattended updates can move Docker or the kernel during a build window with no snapshot - owner must decide whether unattended-upgrades is enabled now or only after launch, and whether Docker is pinned/held
- Docker Compose ownership of the stack versus Pelican - 5.1 rule 1 "Everything runs in Docker Compose. One `docker-compose.yml` describes the entire server... If it is not in the compose file, it does not exist" and rule 2 "All state lives in named bind mounts under one directory, `/srv/laughtail/`" VS the actual environment, where Pelican is already installed on the host and server files live in `/var/lib/pelican/volumes/<server-uuid>/` - the two layouts cannot both be the single source of state - a builder cannot decide whether to abandon Pelican, or to redefine the portability contract around Pelican volumes plus a panel database backup
- Single `mc` service versus two Paper servers - 5.2 lists exactly one Paper service, "`mc` | Paper server" VS the environment's two servers, `laughtail-dev` and `laughtail` - the compose file as specified has no place for the dev server, so config-in-git (rule 5) cannot describe where the build work actually happens - owner must decide whether dev is a second compose profile, a second stack, or stays panel-only
- Repository doc set does not match the governance doc set - 5.6 lists `docs/` as `00-overview.md` through `07-performance.md` plus `decisions.md`, `rejected.md`, `restore-drills.md` VS the standing instruction that `docs/progress.md`, `docs/owner-actions.md`, `docs/questions.md`, `docs/acceptance.md`, `docs/private/` and `docs/spec/` are the files of record - a builder following 5.6 literally would not create the files every session is required to update, or would treat them as out-of-tree
- "Complete" port list has no RCON port number - 5.3 is titled "Ports - the complete list" and 5.5 says "Firewall default-deny inbound; only the table in 5.3 open" VS the table's RCON row, whose Port cell reads "RCON" rather than a number - a default-deny firewall rule cannot be written from a non-numeric port - the builder must be told the RCON port (25575 is only the vanilla default) before the firewall is authoritative
- Named volumes versus bind mounts under one directory - 5.1 rule 2 says "All state lives in named bind mounts under one directory, `/srv/laughtail/`" VS 5.1 rule 6 and 5.2, which say the database "runs in a container with its own volume" / "Own volume" - in Docker a named volume lives under `/var/lib/docker/volumes`, not under `/srv/laughtail/`, so the two rules select different storage mechanisms and the "rsync one directory" migration only works for one of them
- Border defaults are stated in two places with different ownership - 6.5 says "Defaults in Section 23: Overworld 6,000; Nether 2,000; End 3,000" VS 7.1, which states the same three values plus "Resource | 3,000" in its own table - three sections now assert the same numbers, and 6.5 omits the resource world entirely - if any value is ever tuned, a builder cannot tell which section is authoritative

## RISKS ON A 2 vCPU / 4 GB HOST

- Four containers on two cores - 5.2 puts `mc`, `db`, `backup` and `monitor` on the same box; the Paper main thread needs a full core, leaving one core for MariaDB, metrics scraping and backup compression, so any backup run competes directly with the tick loop
- Heap plus MariaDB plus page cache - 6.4 allocates "Around 2.5 GB for the game" on a 4 GB box; MariaDB with default InnoDB buffers plus the OS plus backup compression leaves very little page cache, and `sync-chunk-writes: false` (6.4) makes the server rely on page cache for chunk writes
- Five worlds resident - 7.1 defines Overworld, Nether, End, Resource and Arena; each loaded world carries its own chunk cache, entity tracker and tick loop, multiplying the memory and MSPT cost of the same player count
- Simultaneous multi-world exploration - with a Resource world encouraged for "all serious mining and bulk farming" (7.4) plus the Overworld, the same 24 players can load chunks in two or more worlds at once, which is the worst case for a 2-core CPU
- Monthly resource world regeneration and re-pregeneration - 7.4 regenerates a 3,000 world every month and 6.5 requires pre-generation to the border; Chunky on two cores will saturate the box for a long window, so this must happen with the server closed
- 6-hourly full world snapshots - 5.4 snapshots Overworld, Nether, End and Resource; tar/compression of four worlds on two cores is a sustained MSPT risk unless niced and I/O throttled
- Hourly DB dumps against a live economy - 5.4's hot dump every hour adds a periodic I/O and CPU spike on the same disk the world writes to
- Event scenario at 40 bots in a 100x100 arena with cosmetics on - 6.8 explicitly targets the densest possible entity, damage and particle load, against a 40 ms MSPT ceiling (6.1); this is the scenario most likely to fail
- Claim checks on every block and container interaction - 7.3 makes claims ON with PvP on; a claim lookup on every break, place and container open is a per-event cost that scales with player activity, not with player count
- PvP everywhere with keepInventory false - 7.2 guarantees dropped item stacks on every death; combined with 6.7's ban on entity-clearing plugins, item entity counts during war events are bounded only by natural despawn
- Spawn holograms and live leaderboards - 7.5 requires live leaderboard displays and the Hall of Fame monument at the busiest location; hologram and scoreboard updates tick continuously for every arriving player
- view-distance 6 at 24 players - 6.4's own note calls view distance "Biggest single lever on both CPU and bandwidth"; 24 players at 6 chunks is roughly the ceiling of this box, and 6.8 only predicts "comfortable to roughly 20-24 players"
- Elytra allowed - 7.2 permits elytra, which is the fastest way to force chunk loading; safe only because 6.5 pre-generates to the border, so the mitigation is a hard prerequisite rather than an optimisation
- spark profiling under load - 6.3 requires "minimum 60 seconds of *real* load" with `--thread *`; the profiler itself consumes CPU on a two-core box, so measurements taken this way carry their own overhead
- Restore drill in a throwaway container - 5.4's joinable restored instance would double Paper's memory footprint on a 4 GB box and cannot run alongside the live or dev server
- Monitor scrape frequency - 5.2 requires TPS/MSPT/memory/player exports; a tight scrape interval polls the main thread and is a self-inflicted tick cost if not sampled asynchronously
