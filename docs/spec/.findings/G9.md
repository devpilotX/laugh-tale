## RISKS ON A 2 vCPU / 4 GB HOST

- Resource world reset at the season instant (31.12) regenerates or deletes a world with a 3,000 block border on 2 vCPU, which is heavy sustained disk and CPU; it is scheduled to run "immediately after the season reset job completes", stacking world I/O on top of a single-transaction standings snapshot at the same instant.
- The one-transaction standings snapshot (31.1) holds a write transaction across the whole roster while the database shares 4 GB with Paper; a long transaction at 00:00 IST will spike MSPT if any main-thread call waits on it.
- Combat tag refresh "on every hit given or received" (31.3) runs on the damage event, the hottest event in PvP; any synchronous database write or log flush per hit will breach the 25 ms MSPT target during a 20-player war.
- Combat-log resolution (31.3) performs a full item drop, an Elo award, and a penalty write inside a disconnect handler; disconnect handlers that block on I/O stall the main thread.
- The 30-minute grace "visible countdown" (31.6) implies a per-tick or per-second per-player UI update for every new joiner; naive implementations rebuild the component every tick.
- Illegal item scanning (31.11) inspects NBT and component data and must catch "any container holding another container", which means recursive deep inspection of shulker contents; doing this on every inventory click or container open is expensive on 2 vCPU.
- The crash vectors listed in 31.11, specifically "entity-count and chunk-load abuse" and "firework and elytra chunk-ban patterns", are exactly the loads a 2 vCPU box cannot absorb; chunk generation from elytra flight is single-threaded work in practice.
- Wash-trading and cornering detection (31.10) is pairwise counterparty analysis plus per-player share-of-volume over trade history; run in real time it is superlinear in trade count and must be a batched off-peak job.
- The weekly production report (31.5) aggregates the top ten Berry sources by volume across the economy ledger; a full-table aggregate on a shared 4 GB box will contend with the server unless scheduled away from peak and away from the 00:00 IST reset.
- Retaining "the economy ledger for the life of the server" (31.13) means unbounded table growth on a small disk with a small buffer pool; query cost for 31-7 and 31-8 rises every month unless the ledger is partitioned or rolled up.
- Chat and connection logs kept 90 days and moderation records 2 years (31.13) add further permanent storage on the same box as the game server.
- The generated MOTD (31.7) is computed on every server ping, and pings arrive from listing sites continuously; if generation touches the database per ping rather than a cached value it is a free denial-of-service surface.
- Async tab list updates (31.7) still touch player state; a per-second full tab rebuild for 24 players is cheap only if the rank prefix and ping lookups are cached.
- Taking a host snapshot (33.2) typically causes heavy I/O or a brief pause on the VPS; doing it while a Paper server is running risks a corrupt region file, so snapshots should be taken with both servers stopped.
- Pre-flight items 9 and 11 (33.6) leave a stock server and `laughtail-dev` both present; combined allocations on a 4 GB box exceed the budget, so the stock server must stay stopped, which 33-9 confirms but the checklist does not enforce with a check.
- Pre-flight item 10 (33.6) sets dev heap "at least 25 per cent below its allocation", which on a 4 GB box leaves little room once the database, Wings, and Docker overhead are counted; the margin must be measured, not assumed.
